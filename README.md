# Звіт до лабораторної роботи №10

**Тема:** Інтеграція з REST API: HTTP-клієнт, патерн Repository, керування серверним станом та AbortController.  
**Мета:** Навчитися інтегрувати React-застосунок із зовнішнім REST API. Опанувати поділ архітектури на шари (HTTP Client, Repository, UI State), розмежування серверного та клієнтського стану, скасування мережевих запитів через AbortController, пагінацію даних, перегляд детальної інформації про сутність та коректну візуалізацію всіх станів завантаження (loading, error, empty, success).  
**Застосунок:** Study Planner (планувальник навчальних завдань).  
**Стек технологій:** React 19.3.1, TypeScript 5.8.2, Vite 8.3.5, SCSS (BEM), REST API (DummyJSON), ESLint 10.14.0, Node.js 24.21.0.  
**Гілка проєкту:** feature/rest-api.

## 1. Загальні відомості та реалізований функціонал

У ході лабораторної роботи №10 здійснено перехід від суто локального сховища завдань до повноцінної інтеграції з віддаленим REST API сервісу DummyJSON (`https://dummyjson.com/todos`):

1. **Конфігурація середовища:**
   - Налаштовано змінні середовища через `.env` та створено еталонний файл `.env.example` із параметром `VITE_API_URL=https://dummyjson.com`.
   - Файл `.env` внесено до `.gitignore` для запобігання потраплянню конфігураційних та секретних даних у систему контролю версій.

2. **Розмежування моделей даних (DTO vs Domain Model):**
   - Створено інтерфейси `TodoDto` та `TodosResponseDto` для суворого типізування відповідей API.
   - Створено доменну модель `Task`, яка містить додаткові клієнтські поля (`description`, `priority`, `category`, `pendingDelete`, `userId`).
   - У репозиторії реалізовано чисту функцію мапінгу `mapDtoToTask`, що адаптує віддалені дані до потреб інтерфейсу користувача.

3. **HTTP-клієнт (`httpClient`):**
   - Реалізовано ізольований модуль `src/api/httpClient.ts`, що підтримує уніфіковані методи `get`, `post`, `put`, `patch`, `delete`.
   - Забезпечено коректне формування query parameters через `URLSearchParams`.
   - Створено типізований клас помилок `HttpError` для фіксації HTTP статус-кодів та повідомлень серверних помилок із збереженням первинного виключення в полі `cause`.
   - Реалізовано прозору підтримку сигналу скасування `AbortSignal`.

4. **Патерн Репозиторій (`taskRepository`):**
   - Реалізовано модуль `src/repositories/taskRepository.ts`, що інкапсулює всі операції з віддаленим ресурсом:
     - `getAll({ limit, skip, signal })` — отримання списку завдань із пагінацією;
     - `getById(id, signal)` — отримання одного завдання за його ідентифікатором;
     - `create(data)` — надсилання `POST /todos/add`;
     - `update(id, data)` — надсилання `PUT/PATCH /todos/:id`;
     - `delete(id)` — надсилання `DELETE /todos/:id`.
   - Реалізовано збереження локальних метаданих для полів, які не підтримуються віддаленим навчальним ресурсом.

5. **Розподіл стану на Server State та Client/UI State:**
   - **Server State:** список завдань, статус мережевого запиту (`idle`, `loading`, `success`, `error`), загальна кількість елементів (`total`), кількість на сторінку (`limit`), поточна сторінка (`page`), текст помилки сервера.
   - **Client/UI State:** вибраний фільтр (`all`, `active`, `completed`), рядок текстового пошуку, сортування за пріоритетом, ідентифікатор завдання для модального перегляду (`selectedTaskId`), активне завдання для редагування (`editingTask`), стек тост-сповіщень.

6. **Скасування запитів через `AbortController`:**
   - Під час перемикання сторінок або виклику повторного запиту попередній незавершений запит автоматично скасовується через `controller.abort()`.
   - Помилки `AbortError` коректно фільтруються й не спричиняють виникнення хибного стану помилки в UI.

7. **Пагінація (Pagination):**
   - Реалізовано компонент `Pagination.tsx` із кнопками «Попередня» та «Наступна».
   - Відображається поточна сторінка та загальна кількість сторінок («Сторінка X з Y»).
   - Кнопки автоматично блокуються на граничних значеннях (перша або остання сторінка), а також під час виконання активного завантаження.

8. **Модальне вікно деталей завдання (`TaskDetails`):**
   - До кожної картки додано кнопку «Деталі».
   - При натисканні компонент `TaskDetails` ініціює окремий запит `taskRepository.getById(taskId, signal)` із власним `AbortController`.
   - Відображаються повні дані: ID, назва, опис, пріоритет, категорія, ID користувача та поточний статус виконання.
   - Вікно закривається за кнопкою «Закрити», хрестиком або кліком поза модальним вікном.

9. **Візуалізація всіх станів завантаження:**
   - `loading`: відображення індикатора завантаження (spinner) та повідомлення про очікування відповіді сервера.
   - `error`: відображення повідомлення про помилку та інтерактивної кнопки «Повторити запит» для виклику `refetch()`.
   - `empty`: повідомлення про відсутність завдань (загальне або для обраного фільтра).
   - `success`: рендеринг списку завдань та елементів пагінації.

10. **Збереження архітектурних вимог:**
    - Усі стилі виконані за методологією BEM у файлах SCSS поруч із компонентами.
    - Код повністю відповідає суворому правилу відсутності коментарів.
    - Повна типізація TypeScript без використання типу `any`.

## 4. Відповіді на контрольні запитання

### 1. Яка різниця між Server State та Client State?
- **Server State:** дані, які первинно зберігаються на віддаленому сервері, доступні через асинхронні мережеві запити, можуть змінюватися іншими клієнтами без відома поточного користувача, потребують кешування, обробки станів завантаження, помилок і десинхронізації (наприклад, список `todos` з API, загальна кількість сутностей, деталі конкретного завдання).
- **Client State:** тимчасові дані інтерфейсу, що існують виключно в межах браузера конкретного користувача, змінюються синхронно та не потребують обов'язкового збереження на сервері (наприклад, відкрите/закрите модальне вікно, поточна активна вкладка фільтрації, текст у полі пошуку, стан редагування форми).

### 2. Чому важливо розділяти HTTP-клієнт, репозиторій та компоненти UI?
Такий поділ реалізує принцип єдиної відповідальності (Single Responsibility Principle) та слабкої зв'язності (Loose Coupling):
- **HTTP-клієнт** відповідає суто за виконання мережевих операцій за протоколом HTTP, формування заголовків, кодування тіла запиту, обробку URL-параметрів та помилок мережі.
- **Репозиторій** ізолює бізнес-логіку доступу до конкретної сутності (`Task`), мапить структури даних сервера (DTO) у доменні моделі інтерфейсу і навпаки. Якщо структура API або кінцеві точки зміняться, редагуванню підлягає лише репозиторій, а не весь код застосунку.
- **UI-компоненти** займаються виключно відображенням даних, реагуванням на дії користувача та декларативним описом інтерфейсу, не знаючи технічних деталей мережевих викликів (`fetch`, заголовки, статус-коди).

### 3. Для чого потрібен AbortController і як він запобігає race conditions?
`AbortController` дозволяє програмно скасувати виконання активного мережевого запиту `fetch`. При швидкому перемиканні користувачем сторінок або параметрів фільтрації запити можуть завершуватися не в тому порядку, у якому їх було надіслано (Race Condition). Скасування попереднього запиту через `controller.abort()` у функції очищення (`cleanup`) хука `useEffect` гарантує, що відповідь від застарілого запиту буде відхилена браузером і не перезапише свіжі дані в стані компонента.

### 4. Чому помилку `AbortError` потрібно відфільтровувати під час обробки виключень?
Скасування запиту через `AbortController` є штатним керованим сценарієм роботи інтерфейсу (наприклад, користувач перейшов на іншу сторінку або закрив модальне вікно до завершення завантаження), а не апаратною чи мережевою несправністю. Якщо не відфільтрувати `AbortError`, користувачу буде безпідставно показано екран помилки «Не вдалося завантажити дані», хоча насправді система коректно відкинула непотрібну відповідь.

### 5. Як реалізувати пагінацію на базі параметрів limit та skip?
Параметр `limit` визначає максимальну кількість записів, яку сервер повертає в одній відповіді. Параметр `skip` вказує кількість записів, яку необхідно пропустити від початку вибірки.  
Розрахунок зміщення для довільної сторінки `page` (починаючи з 1) виконується за формулою:
```text
skip = (page - 1) * limit
```
Загальна кількість сторінок обчислюється як:
```text
totalPages = Math.ceil(total / limit)
```

### 6. Які переваги надає мапінг API DTO у внутрішню доменну модель?
1. Захист інтерфейсу від змін структури даних бекенду: якщо бекенд змінить назву поля (наприклад, `todo` на `title`), зміна вноситься в одній функції мапінгу `mapDtoToTask`, а всі UI-компоненти залишаються без змін.
2. Збагачення моделі: доменна модель може містити додаткові поля, потрібні виключно для клієнтської логіки (`priority`, `category`, `pendingDelete`), які відсутні у базовому API.
3. Гарантія типів: приведення типів даних, встановлення значень за замовчуванням та валідація формату виконуються на межі отримання даних.

## 5. Порядок демонстрації на захисті

1. **Завантаження списку завдань із DummyJSON REST API:**
   - Відкрити застосунок: продемонструвати початковий стан `loading` (spinner), після чого завантажується перша сторінка завдань із віддаленого ресурсу `https://dummyjson.com/todos?limit=10&skip=0`.
2. **Пагінація та блокування кнопок:**
   - Натиснути кнопку «Наступна» — завантажується сторінка 2 (`skip=10`), відображається текст «Сторінка 2 з X».
   - Перейти на сторінку 1: переконатися, що кнопка «Попередня» автоматично стає неактивною (`disabled`).
3. **Перегляд деталей завдання (GET `/todos/:id` з `AbortController`):**
   - На будь-якій картці натиснути кнопку «Деталі».
   - Відкривається модальне вікно, у якому відображається окремий індикатор завантаження під час виконання запиту `taskRepository.getById()`.
   - Продемонструвати успішно завантажені дані: ідентифікатор, назву, категорію, пріоритет, ID користувача та статус виконання.
   - Закрити вікно натисканням на хрестик або клавішу «Закрити».
4. **Створення завдання через API (POST `/todos/add`):**
   - Заповнити форму «Додати завдання» та натиснути кнопку відправки.
   - Застосунок надсилає POST-запит на DummyJSON, отримує відповідь із новим ID, додає завдання на початок списку та відображає підтверджувальний тост.
5. **Редагування завдання через API (PUT/PATCH `/todos/:id`):**
   - Натиснути кнопку «Редагувати» на картці завдання.
   - Форма заповнюється даними завдання та переходить у режим редагування.
   - Змінити текст або пріоритет і натиснути «Зберегти зміни». Запит надсилається на сервер, локальний стан оновлюється.
6. **Видалення завдання через API (DELETE `/todos/:id`):**
   - Натиснути кнопку «Видалити».
   - Завдання переходить у стан очікування із можливістю скасування (Undo) через Toast.
   - Після завершення таймера надсилається запит на видалення до API та елемент видаляється зі стану.
7. **Обробка стану помилки та повторення запиту (Retry):**
   - Змінити значення `VITE_API_URL` на недоступну адресу або вимкнути мережу в DevTools.
   - Перемкнути сторінку: відображається стан помилки із повідомленням та червоною кнопкою «Повторити запит».
   - Відновити зв'язок і натиснути «Повторити запит»: дані успішно завантажуються знову.
8. **Перевірка коду та лінтера:**
   - Запустити `npm run lint` — 0 помилок, 0 попереджень.
   - Запустити `npm run build` — успішна збірка TypeScript і Vite.
