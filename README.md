# Звіт до лабораторної роботи №9

**Тема:** React State та Effects: Context API, useReducer, useEffect і Custom Hooks.  
**Мета:** Навчитися організовувати стан React-застосунку, коли одного локального useState стає недостатньо. Опанувати підняття стану, Context API, useReducer, побічні ефекти, роботу з localStorage та створення власних hooks.  
**Застосунок:** Study Planner (планувальник навчальних завдань).  
**Стек технологій:** React 19.3.1, TypeScript 5.8.2, Vite 8.3.5, SCSS (BEM), ESLint 10.14.0, Node.js 24.21.0.  
**Гілка проєкту:** feature/state-effects.

## 1. Загальні відомості та реалізований функціонал

У ході лабораторної роботи №9 виконано рефакторинг та розширення навчального застосунку Study Planner без втрати функціоналу лабораторної роботи №8:
1. **Рефакторинг стану на useReducer:** Основний масив завдань переведено на керування через чисту функцію `taskReducer`. Реалізовано обробку дій: `add`, `toggle`, `update`, `requestDelete`, `confirmDelete`, `undoDelete`, `clearCompleted`, `reset`.
2. **Context API:** Створено `TaskContext` та `TaskProvider`. Спільний стан і методи передаються до компонентів безпосередньо через Context, що усунуло проблему prop drilling.
3. **Редагування завдань:** Додано можливість зміни полів завдання (назва, опис, категорія, пріоритет) через форму `TaskForm`.
4. **Механізм Undoable Delete:** Замість негайного видалення завдання позначається як таке, що очікує видалення. Запускається 5-секундний таймер зворотного відліку, під час якого користувач може скасувати дію кнопкою «Скасувати». При завершенні таймера завдання видаляється остаточно.
5. **Власний компонент Toast:** Реалізовано спливаючі повідомлення зворотного зв'язку без сторонніх бібліотек. Toast відображає статуси створення, редагування, видалення, скидання даних, а також прогрес зворотного відліку Undoable Delete.
6. **Робота з localStorage та useEffect:**
   - Читання збережених завдань при старті з обробкою помилок `JSON.parse`.
   - Синхронізація актуального списку завдань зі сховищем браузера при кожній зміні через `useEffect`.
7. **Синхронізація із заголовком вкладки:** Реалізовано побічний ефект через `useEffect`, який динамічно оновлює `document.title` відповідно до кількості невиконаних завдань.
8. **Кастомні хуки (Custom Hooks):**
   - `useTaskContext()` — забезпечує доступ до контексту з перевіркою виклику всередині `TaskProvider`.
   - `useLocalStorage<T>()` — універсальний хук для роботи з `localStorage`, використаний для збереження обраного фільтра.
9. **Кнопка «Скинути дані»:** Повертає початковий набір завдань `initialTasks`.
10. **Збереження функціоналу ЛР №8:** Фільтри (всі, активні, виконані), лічильники на кнопках, пошук за підрядком, сортування за пріоритетом, розрахунок статистики без зайвого стану та умовний рендеринг повідомлень при порожніх списках.
11. **Реалізовані додаткові завдання (пункт 11 методички):**
    - **Синхронізація між вкладками:** Реалізовано слухач події `storage` у `TaskProvider`. При зміні завдань в одній вкладці браузера, всі інші відкриті вкладки автоматично оновлюють список через дію `sync` без перезавантаження сторінки.
    - **Окремий ThemeContext:** Реалізовано `ThemeContext` та `ThemeProvider` із збереженням обраної теми (`light` / `dark`) у `localStorage` через кастомний хук `useLocalStorage`, з перемикачем у шапці `Header` та підтримкою теми на рівні SCSS.
    - **Оптимізація Context value:** Значення контекстів `TaskContext` та `ThemeContext` оптимізовано за допомогою `useMemo`, а всі методи-обробники обгорнуто в `useCallback`. Завдяки цьому при рендерингу провайдера не створюються нові посилання на об'єкти та функції без зміни залежностей.

## 4. Відповіді на контрольні запитання

### 1. Коли state доцільно піднімати у батьківський компонент?
Підняття стану (Lifting State Up) доцільне тоді, коли декілька дочірніх компонентів на одному або різних рівнях ієрархії повинні відображати однакові дані або змінювати один і той самий стан. Стан переноситься до їхнього найближчого спільного предка, який стає єдиним джерелом правди.

### 2. Що таке prop drilling і яку проблему вирішує Context API?
Prop drilling — це процес передачі props через проміжні компоненти, яким ці дані насправді не потрібні, виключно для доставки дочірньому компоненту на нижчому рівні дерева. Context API вирішує цю проблему, створюючи глобальну або модульну область видимості даних, з якої будь-який компонент-підписник може отримати стан безпосередньо.

### 3. Що таке reducer? Чим reducer відрізняється від звичайної функції оновлення state?
Reducer — це чиста функція, яка приймає поточний стан (state) та об'єкт дії (action), а повертає новий стан: `(state, action) => newState`. На відміну від звичайної функції оновлення стану (`setState`), reducer інкапсулює складну логіку переходу між станами в одному місці відповідно до чітко визначених типів дій, розділяючи «що сталося» (dispatch action) від «як змінився стан» (reducer).

### 4. Якою повинна бути чиста reducer-функція?
Чиста функція reducer повинна:
1. За однакових вхідних аргументів завжди повертати однаковий результат.
2. Не модифікувати (не мутувати) аргументи, а повертати нові об'єкти та масиви.
3. Не містити жодних побічних ефектів (side effects): не виконувати мережевих запитів, не звертатися до DOM, не працювати з localStorage, не запускати таймери (setTimeout, setInterval).

### 5. Що таке action і dispatch?
Action — це звичайний JavaScript-об'єкт, який описує подію, що відбулася в застосунку. Зазвичай містить обов'язкове поле `type` (тип дії) та опціональне поле `payload` (додаткові дані для оновлення).  
Dispatch — це функція, яку повертає `useReducer`, призначена для відправки action у reducer для ініціації зміни стану.

### 6. Коли useReducer доцільніше використовувати за useState?
`useReducer` доцільніше використовувати, коли:
- Логіка стану є складною та включає багато взаємопов'язаних підполів.
- Наступний стан суттєво залежить від попереднього.
- Необхідно підтримувати кілька різних сценаріїв зміни стану (додавання, редагування, видалення, скидання).
- Потрібно спростити тестування логіки переходу станів окремо від компонентів.

### 7. Що таке Context API і з яких основних частин складається його використання?
Context API — це вбудований механізм React для передачі даних через дерево компонентів без явного прокидання props.  
Складається з трьох частин:
1. Створення контексту за допомогою `createContext()`.
2. Огортання дерева компонентів у провайдер `<Context.Provider value={...}>`.
3. Отримання значення в дочірньому компоненті через хук `useContext(Context)`.

### 8. Чи потрібно через Context передавати весь state застосунку?
Ні, передавати весь стан застосунку в один контекст є антипатерном. Контекст слід використовувати лише для справді спільного стану (тема, автентифікація, глобальний список сутностей). Локальний стан форми або тимчасові значення інпутів повинні залишатися всередині компонентів через `useState`. Крім того, зміна значення контексту викликає повторний рендеринг усіх компонентів-підписників, тому контексти варто розділяти за зонами відповідальності.

### 9. Що таке side effect у React?
Side effect (побічний ефект) — це будь-яка операція, яка взаємодіє із зовнішнім середовищем поза чистим обчисленням JSX у процесі рендерингу компонента. Приклади: прямі маніпуляції з DOM, мережеві запити (fetch, REST API), читання/запис у `localStorage`, запуск і зупинка таймерів (`setTimeout`, `setInterval`), підписка на зовнішні події браузера.

### 10. Для чого використовується useEffect?
Хук `useEffect` використовується для виконання побічних ефектів у функціональних компонентах після завершення процесу рендерингу та монтування вузлів у DOM, а також для синхронізації стану компонента із зовнішніми системами.

### 11. Коли запускається Effect і коли виконується cleanup?
- Ефект запускається після завершення рендерингу та оновлення DOM: при першому монтуванні компонента, а також після кожного рендерингу, якщо змінилося хоча б одне значення з масиву залежностей `deps`.
- Функція очищення (cleanup), яку повертає ефект, виконується:
  1. Перед наступним повторним запуском цього ж ефекту (якщо залежності змінилися).
  2. У момент повного розмонтування (unmount) компонента з DOM.

### 12. Чому запис у localStorage є побічним ефектом?
Запис у `localStorage` взаємодіє із зовнішнім синхронним API браузера, яке не є частиною життєвого циклу Virtual DOM React. Виклик операцій вводу-виводу безпосередньо під час фази обчислення рендеру порушує чистоту компонента, сповільнює рендеринг та може викликати некоректну поведінку при конкурентному рендерингу.

### 13. Чому timer для Undoable Delete не можна створювати всередині reducer?
Reducer повинен бути абсолютно чистою детермінованою функцією. Створення таймера (`setTimeout` або `setInterval`) є асинхронним побічним ефектом, який залежить від часу та зовнішнього середовища. Якщо створити таймер у reducer, його неможливо буде безпечно очистити при розмонтуванні або відміні, а повторні виклики reducer (наприклад, у `StrictMode`) створять витік пам'яті та дублювання таймерів.

### 14. Для чого потрібен clearTimeout у cleanup?
`clearTimeout` (або `clearInterval`) у функції очищення необхідний для скасування відкладеного виконання дії, якщо компонент розмонтувався або користувач скасував операцію (наприклад, натиснув «Скасувати» під час Undoable Delete). Це запобігає витокам пам'яті, спробам оновлення розмонтованого стану та помилковому виконанню дій після зміни наміру користувача.

### 15. Чому не варто дублювати derived state?
Derived state (похідний стан) — це дані, які можуть бути обчислені на основі вже наявного стану (наприклад, кількість виконаних завдань, відфільтрований список, середнє значення). Дублювання таких даних в окремий стан (`useState`) вимагає ручної синхронізації, ускладнює код, створює загрозу розсинхронізації та призводить до зайвих циклів рендерингу.

### 16. Що таке Custom Hook?
Custom Hook (власний хук) — це JavaScript-функція, назва якої починається з префікса `use`, яка всередині викликає стандартні хуки React (`useState`, `useEffect`, `useReducer`, `useContext` тощо). Власні хуки призначені для винесення та повторного використання логіки роботи зі станом між різними компонентами без дублювання коду.

### 17. Які правила потрібно дотримуватися при створенні власних hooks?
1. Назва хука обов'язково повинна починатися з дієслова `use` (наприклад, `useLocalStorage`, `useTaskContext`).
2. Хуки можна викликати лише на верхньому рівні: заборонено викликати хуки всередині циклів, умовних конструкцій (`if`) або вкладених функцій.
3. Хуки можуть викликатися лише з функціональних компонентів React або інших кастомних хуків.

## 5. Порядок демонстрації на захисті

1. **Створення та редагування завдання:**
   - Додати нове завдання через форму, показати Toast «Нове завдання успішно додано».
   - Натиснути кнопку «Редагувати» на завданні, змінити пріоритет або назву, зберегти та показати Toast «Завдання успішно оновлено».
2. **Демонстрація Undoable Delete:**
   - Натиснути кнопку «Видалити» на будь-якому завданні.
   - Завдання переходить у приглушений стан «Очікує видалення (5 сек)...».
   - З'являється Toast зі зворотним відліком від 5 до 0 секунд та кнопкою «Скасувати».
   - Натиснути «Скасувати» — видалення скасовується, завдання повертається до звичайного стану.
   - Натиснути «Видалити» ще раз і зачекати 5 секунд — завдання остаточно видаляється зі списку, а таймер очищається.
3. **Збереження у localStorage:**
   - Додати або відредагувати завдання, перезавантажити сторінку в браузері (F5) — дані успішно відновлюються.
4. **Синхронізація з браузером:**
   - Продемонструвати зміну заголовка вкладки браузера відповідно до кількості невиконаних завдань.
5. **Аналіз коду в редакторі:**
   - `src/context/taskReducer.ts`: чиста функція, типи actions.
   - `src/context/TaskProvider.tsx`: використання `useReducer`, `useEffect` для `localStorage` та таймера.
   - `src/hooks/useTaskContext.ts` та `src/hooks/useLocalStorage.ts`: власні хуки.
   - Відсутність помилок у консолі: `npm run lint`.
